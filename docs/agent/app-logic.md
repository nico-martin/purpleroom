# purpleroom app logic

This is the living reference for the app's current product behaviour. It describes what members can do, who can see which data, and how features interact—not an implementation plan or change log.

Update the relevant sections whenever behaviour changes, in the same change as the implementation and tests. Keep one coherent set of rules here rather than adding a second specification that supersedes this one. Record future ideas separately and label them as unimplemented. If code and an agreed privacy rule disagree, report the discrepancy rather than silently redefining the rule.

Development conventions are in [AGENTS.md](../../AGENTS.md). Hosting and upgrade procedures are in [the deployment guide](../deployment.md). Previous product designs remain available in Git history.

## 1. Purpose and concepts

purpleroom helps conference speakers discover opportunities, privately manage proposals, and share experience and plans with accepted friends.

| Concept | Meaning |
| --- | --- |
| Member | An account with a verified email and completed display name. |
| Admin | A member with additional catalog and account-management permissions. |
| Conference | A long-lived event brand, such as JSNation. |
| Edition | A particular event with its own title, dates, location, and CFP information. |
| Talk / proposal | A reusable, privately owned entry in a member's library; called a `paper` internally. |
| Submission | An owned speaking opportunity for an edition, optionally linked to a proposal, with a privately tracked status. |
| Attendance | A manually selected Going or Maybe marker for an edition. |
| Crew | The current member's mutually accepted friends. There are no separate named crews. |
| Speaker review / take | A member's conference-level experience, shared with their friends. |

## 2. Access, signup, and profiles

- All catalog, ordinary member, review, proposal, attendance, and social content requires login. Open-web exceptions are explicitly opted-in speaker press kits and speaker-image capability URLs described below. Elsewhere “public” within the app means visible to signed-in members, not the open web.
- Sign-in, email verification, the public FAQ at `/faq`, and the minimal application shell/assets must be reachable before login. The health endpoint exposes only service status. First-install setup is separately secret-protected.
- Login/verification links to the public FAQ, which explains the purpose, intended audience, signup, core features, crew visibility, proposal privacy, external CFP submission, and beta status. Questions start collapsed and expand independently using pointer or keyboard controls. The FAQ links back to sign-in and supports both appearance themes; it contains only static introductory information, never member or catalog data.
- Introductory copy describes a members-only space without blanket claims that no information is public. Specific proposal and submission privacy rules still apply; this wording does not grant anonymous access to protected data.
- Signup and login use one passwordless email flow. Addresses are trimmed, lowercased, and matched case-insensitively.
- Requesting a code does not create an account. Successful verification creates a member account if the address is new, or signs into the existing account.
- Signup/login sends a six-digit numeric code (including possible leading zeroes), not a link. Codes expire after 15 minutes, can be consumed once, and stop working after five wrong guesses. A newly issued code invalidates previous codes for that address. Verification/consumption and attempt increments are atomic. Wrong guesses also count against one budget per address across all of its request IDs: after 20 wrong codes in a fixed 24-hour window, that address cannot verify codes (even correct ones) and new requests send no code until the window resets. The response remains the generic invalid-code/request shape.
- Codes are bound to a high-entropy request ID returned to the requesting browser; only hashes of the request ID and request-ID/code combination are stored. Verification requires both the request ID and code. The code alone cannot be used with a different request. Public request responses have the same shape for valid addresses regardless of signup/account/suspension/throttling/delivery state; only development responses additionally expose the code.
- The login screen provides one paste-friendly text field with a numeric keyboard and one-time-code autofill. Pasted spaces/separators are removed and leading zeroes are preserved. The email/request ID (never the entered code) survive reload in tab-scoped session storage, and are cleared on success or change-email. The intended in-app destination is preserved. Resend is available after a 60-second UI cooldown; server-side limits are 5 requests/address/IP/hour, 20 requests/address/hour, 30/IP/hour, 100 verification attempts/IP/hour, and 20 wrong codes/address/24 hours.
- Signup/sign-in emails are strictly transactional: a lightly purple-branded HTML layout with a large selectable code, instructions to paste it into the original browser, expiry/safety text, and an equivalent plain-text alternative. They contain no tagline, project-credit/footer links, authentication links, hidden preview text, remote images, or tracking pixels. Already-issued email links and local CLI seed links remain usable through the legacy verification route; new public requests never issue links.
- Production uses authenticated, certificate-verified SMTP when configured, otherwise the host's PHP `mail()` transport. SMTP requires encryption; a failed configured SMTP delivery does not silently fall back to another transport. Development displays the local code without sending email or logging it.
- The development frontend's login form explains the local admin address (`admin@purpleroom.dev`), member defaults for other new addresses, preservation of existing roles, and how to use the displayed code without sending mail when the API is also in development mode. These instructions are omitted from production builds.
- Delivery failures discard the unusable pending code, log only a safe diagnostic, and retain the same generic public request response. SMTP credentials, production codes, and authentication tokens must never be exposed in responses or logs. This does not introduce crew-request or other social notification emails.
- Anonymous API requests never create server-side session files. A session is started only when signing in (or during first-install setup); requests with an unknown or signed-out session cookie are answered as unauthenticated, their empty session is discarded, and the cookie is cleared. Logout without a session cookie is a no-op.
- The normal production request response does not reveal whether an account exists or whether a request was throttled. Suspended accounts cannot sign in.
- New accounts must choose a nonblank display name before appearing in the directory or accessing normal app features. The email address is never used as an automatically public display name.
- Members edit their own display name and optional profile image in **Settings**, and their homepage and social links in **Speaker settings**. Their own Settings show their email; member directory and profile responses do not expose email addresses or authentication tokens.
- A profile image is imported from a URL on save, validated like conference logos, and stored locally under private avatar storage. The saved `avatar_url` points to an authenticated API route, not the external source. Existing remote avatars migrate on the next profile save, never on ordinary reads.
- Keeping a stored avatar reuses it without another download. Members can replace or remove it; removal returns to initials without purging retained historical files. Import/validation/storage failure leaves all profile fields unchanged.
- Avatar serving follows member visibility: signed-in members may see active, completed profiles' images unless blocked in either direction. Suspended profiles and stale/removed image URLs are unavailable. Direct filesystem access is denied.
- Optional links are **Homepage, GitHub, LinkedIn, X, Bluesky, Instagram, YouTube, and Mastodon**. They require full HTTP(S) URLs without embedded credentials; Mastodon may use any instance. Empty values clear a link; omitted fields retain their values.
- Saved links appear on member profiles for signed-in viewers, including non-friends; blocked/suspended profile restrictions still apply. These links do not grant access to attendance, reviews, or private submissions. Compact member identity responses need not include the links.
- Members can permanently delete their own account from **Settings → Danger**, after reading an irreversible-deletion warning and typing `DELETE` in a confirmation dialog. The server enforces this confirmation and only deletes the authenticated account; admins cannot delete other members through this action. Self-service email changes and data export are not provided.

### Private speaker information and public press kits

- Public press-kit pages stay focused on the speaker and do not show a sign-in call to action. Public JSON API and OpenAPI links sit in a separate **Profile data and integrations** section explaining their read-only, no-sign-in purpose for event websites/tools, with individual descriptions distinguishing profile JSON from the API specification. These are not personal/social links.
- Cover uploads are prepared locally in the browser: decode with EXIF orientation, centre-crop to 4:1, downsize to at most 1600 × 400 without upscaling, and encode as WebP (PNG fallback). Large original files may exceed 5 MB because they are never uploaded; the prepared file must be within 5 MB. Invalid/unsupported or undersized images and decode/encoding failures show actionable errors and send no upload. Controls show preparation/upload progress and prevent duplicate saves; selecting a replacement clears errors. Server-side image, size and dimension validation still applies to the prepared upload.
- **Speaker toolkit** at `/speaker` is an owner-only, read-only copy/download workspace, separate from the public press kit. It shows saved information regardless of what is published, with no editing, picture removal, draft-profile preview or publication controls. Neither friends nor admins can retrieve another member's private toolkit. It remains private even when the member publishes a press kit. Private talk-library content is not part of the toolkit payload (`GET /speaker`); the Papers section below reads it separately in the owner's browser.
- The toolkit's **Papers** section has a **Talk** dropdown of the owner's own talks (from the owner-only `GET /papers`, most recently updated first; the first is selected by default). The selected talk is shown open with copy actions and character/word counts for its title, set details (duration or duration range, audience level, language, format) and every abstract variant, plus an **Edit this talk** link to its talk page. Switching is local UI state, not a save. Talk notes and submissions are not shown. Without talks it shows a **Create a talk** link to `/talks/new`. It appears even when no speaker information has been saved, offers no editing or publication control, and is never part of the public press kit or its JSON.
- **Speaker settings** at `/settings/speaker`, immediately below Settings in sidebar navigation, is where members edit speaker information, username, homepage/socials, picture imports/removal and publication. It maintains owner-only tagline, company, job title, an optional separately entered public contact email, up to 20 named bio variants (for lengths or languages), up to ten labelled pictures with credits/usage instructions, and up to 50 manually entered talks/recordings/slides/appearances. Links reuse the existing eight profile-link fields and keep their existing signed-in member visibility; moving the form does not change their audience. General Settings retains appearance, display name, profile image and account deletion; its saves omit speaker fields and do not clear them.
- Toolkit text is itself a labelled, keyboard-accessible copy action with a small leading copy icon. Clicking either the text (including URL text) or icon copies the full value without navigating or changing data. On success the icon changes to a checkmark and a screen-reader status announces success; the original text stays visible. Enter/Space work too. Clipboard failure leaves the copy icon and offers a manual-copy dialog that preserves multiline bios.
- Toolkit and press-kit bios use a **Bio variant** dropdown, showing/copying only the selected variant's text (first by default). Switching is local UI state, not a save or a change to what is published; the public JSON still contains every published bio. Both views use the same padded, content-width copy controls, with leading copy/check icons vertically centred alongside names and multiline text. Hover backgrounds fit the content rather than spanning the row; long text still wraps within its container. Toolkit URL text copies on click; press-kit URLs open in a new tab, with a separate leading icon that copies the URL without navigation.
- New speaker pictures can be uploaded as local files or imported from URLs in Speaker settings. They must be PNG, JPEG, WebP or AVIF, at least **2000 pixels wide** after EXIF orientation, at most 5 MB, 20 megapixels and 8192px on either encoded edge. URL imports retain shared pinned-DNS/SSRF, size and timeout validation; no untrusted remote preview is rendered. SVG/GIF/ICO remain supported for avatars/logos but not new speaker pictures. PHP GD performs bounded resizing; JPEG orientation uses EXIF. Validation/generation completes before any picture row is stored; failure leaves existing images/information unchanged.
- Saving generates **S 400px, M 720px, L 1080px, XL 1900px**, and **Full**. Sizes specify width, with proportional height rounded to the nearest pixel, never cropping, padding or stretching the stored image. Full preserves the exact original bytes, including metadata; generated variants have normalised orientation and strip source metadata. JPEG variants use JPEG; other raster variants use WebP when available, otherwise PNG. Legacy originals remain accessible as Full-only without regeneration during reads or a new minimum-width requirement; replace them to generate sizes. Existing publications are not modified automatically.
- Toolkit, settings and public-profile picture grids show three cards per desktop row, two on medium screens and one on mobile. Cards share a **3:2 landscape**, theme-matched preview with `object-contain`, showing the complete original aspect ratio with letterboxing as needed. The blank area uses the current appearance's divider colour, not fixed white. Previews always load **M (720px)** when available, falling back to the original; size selection does not reload larger images. S/M/L/XL/Full controls select the exact byte-based file size, width/height and download/copy target, independent of the M preview. **Copy image** writes a PNG representation of that selected size to the clipboard; unsupported/denied clipboard access produces actionable feedback instead of claiming success. **Copy URL** copies the selected variant's absolute, public capability URL. Downloads preserve the selected stored format. No old-picture or sign-in-required notice appears in these cards.
- Homepage/social links use a **two-column grid** in the toolkit and public press kit on medium/wide screens, stacking to one column on mobile. Long URLs wrap within their column. Toolkit links still copy; public-profile links still open externally with a separate copy icon.
- Picture cards use compact, single-row size controls and copy actions; file sizes and pixel dimensions stay on one line even in the three-column layout. The visible download label is simply Download, with the picture name retained in its accessible label.
- Every saved speaker picture has a stable, random 192-bit public token. `GET /api/speaker-pictures/{token}` and its `/download`, `/sizes/{size}`, `/sizes/{size}/download` routes serve image bytes without login, even when the speaker profile is private/unpublished. Anyone holding a URL can view it, including blocked viewers; there is no public picture listing, account payload or numeric-ID lookup. Upload/import copy explains this before saving. All sizes share the same token. Removal, owner suspension/incompletion or account deletion denies subsequent requests; restoration restores access to retained images. Unpublishing or renaming the profile does **not** revoke these image URLs. Cache headers remain no-store and serving is sandboxed/nosniff, with the shared public rate limit and no anonymous sessions.
- Original and generated image files stay in protected, hash-named avatar storage and are covered by the existing durable account-deletion queue, including retained replacements and failed-save leftovers. Removing a picture revokes all its public image URLs and owner reads; retained files are not otherwise purged automatically. Ordinary member avatar routes remain authenticated and retain block/visibility checks. Prior revision-scoped speaker-media routes remain compatible and publication-gated, but current picture responses use stable public token URLs.
- Speaker settings allows an optional unique username of **4–40** lowercase ASCII letters/numbers separated by single dashes, with no leading/trailing/repeated dashes. A 350ms-debounced typeahead checks availability after valid input, cancels obsolete requests and ignores stale responses. Too-short/invalid, checking, available, current, taken and network-failure states have accessible feedback. Known-invalid/taken or pending names cannot be saved; network failure still permits a server-validated save. The authenticated, profile-completed-only `GET /api/speaker/username-availability?username=…` returns only the candidate and availability, not owner/account data; it is no-store and limited to 120 checks/member/minute. Own current usernames count as available.
- Claims are rechecked under a write lock and enforced by a unique database index; an availability response does not reserve a name. Reserved names in `api/lib/reserved-usernames.php` (including `purpleroom`, `purple-room`, `example` and dash variants) are indistinguishable from already-claimed names: both report unavailable and saving returns the same 409 `username_taken` error. The UI does not describe a reserved-name policy. Suspended accounts keep their claims. New claims require four characters; existing values are not rewritten, and unrelated link/profile edits omit an unchanged username. Changing/clearing a claim unpublishes the kit and retires the old URL; otherwise the canonical path is `/u/{username}`. A claim alone never publishes anything.
- Press kits have a LinkedIn-style masthead: a wide **4:1 cover** above a circular portrait overlapping its lower edge, followed by the name and speaker details. The portrait uses the owner's saved **Purple Room profile picture**, changed in General Settings; without a saved local picture it shows initials. Speaker settings has no portrait/gallery selector. Publishing/updating explicitly includes a snapshot copy of the saved profile picture; later avatar changes do not change an existing publication. No remote avatar is fetched during preview/publication; legacy remote avatars must first be saved in Settings.
- The Header image is a **separate custom file upload**, not a gallery selection. Recommended dimensions are **1600 × 400**, minimum 800 × 200; PNG/JPEG/WebP/AVIF, up to 5 MB and the shared image limits. Server-side GD normalises EXIF orientation and centre-crops/resizes to exactly 4:1 (maximum 1900px wide), stripping metadata. Save cover image and Remove cover image change only the draft, not the current publication. The saved cover is previewed with the account portrait, in both themes and on mobile. Covers do not count toward or appear in the speaker-picture gallery. Previous header choices are retained until replaced/removed; stored legacy portrait choices and published snapshots are preserved, but new publication uses the account picture.
- Custom covers and profile-picture snapshots use owner-bound branding assets in protected avatar storage and the account-deletion cleanup queue. Private reads require ownership, even for admins. Publication-gated `/api/speaker-branding/{token}` URLs serve only assets referenced by the current active/completed owner's published snapshot, with no-store, sandbox/nosniff, public throttling and no anonymous sessions. They never expose the authenticated `/api/avatars/` path. Unpublishing/updating away from an asset, suspension, or account deletion denies subsequent branding reads. This is distinct from gallery pictures' independent public capability URLs. Saving unrelated text/links retains the custom cover; default is a themed blank cover and profile-picture/initials portrait.
- **Make my profile public**, in Speaker settings only, is a sliding switch, off by default for every account. Turning it on directly publishes **all saved speaker-profile information**: display name, tagline, company, job title, separately entered public contact email, all bio variants, all saved profile links, speaker pictures with credits/usage instructions, and all manually entered talks/recordings/slides/appearances. There is no sharing checklist or mandatory preview. An optional private preview shows the full saved profile without publishing it. The switch remains operable: a missing username or unsaved edits produces an actionable error rather than an inert disabled control. Unsaved edits must be saved before publishing/updating; turning public sharing off remains available even while editing. Enter/Space and pointer activation work, with the thumb moving left for private and right for public.
- Publication stores a complete server-allowlisted speaker-profile snapshot separate from private draft data and account responses. Saving speaker information, changing a signed-in profile or adding pictures does not change that snapshot. **Update public profile** explicitly replaces it with all current saved speaker information, without requiring preview. Publication requests require explicit `publish_all: true`; old partial-selection requests are rejected rather than silently broadening previous consent. Existing stored snapshots are not automatically expanded. Login email is never copied into contact details. No proposal/submission linking or automatic conversion is provided: public work is entered independently, and private proposal titles, content, IDs, submission outcomes/dates/notes, account tokens, crew, reviews and private plans never enter a kit. Removing a published picture also unpublishes the kit rather than leaving stale consent.
- Anonymous visitors can view only a published, completed, active member's speaker-profile snapshot at `/u/{username}` and `GET /api/public/speakers/{username}`. The JSON has `schema_version`, a random stable `speaker_id` (independent of username), canonical URLs and the saved speaker-profile fields; empty optional text fields may be omitted. Published pictures use separate public routes, not the authenticated avatar route. Existing block rules still protect signed-in member/social content; a deliberately public press kit is visible on the open web, including to anonymous or blocked viewers.
- Public profile data uses `no-store` and rechecks publication/suspension. Unpublishing, deletion, username changes, removal of a published picture, or suspension stops public profile/API access on subsequent requests. Stable public image URLs follow the independent lifecycle above; only legacy revision-scoped URLs rotate with publication. Restoring a suspended account makes a still-published kit and retained image URLs visible again. Downloaded or third-party cached copies cannot be recalled. Public profile pages do not load private member APIs or create sessions.
- Public JSON, picture and profile-HTML routes share a 120-requests/IP/60-seconds budget using the direct peer address, not untrusted forwarded headers. Excess requests return 429 with `Retry-After: 60`; missing, private and suspended JSON/media return the same 404. `/u/{username}` serves the existing SPA shell with server-rendered metadata only for published, active/completed profiles; unavailable profiles get the same generic shell without identity/OG tags. Machine-readable OpenAPI documentation and examples are served at `/speaker-openapi.json`; detailed consumer guidance is in `docs/public-speaker-api.md`. There are no public write or private-account automation APIs.
- Published press kits integrate **Shareable** at `https://shareable.nico.dev/`. Initial HTML includes escaped title/description/canonical and Open Graph/Twitter image metadata, so non-JavaScript crawlers can find it. Image URLs point to `/render?url={canonical public profile}&version={template version + publication revision}` (Twitter adds `format=twitter`); publishing/updating rotates the version, while private draft edits do not. The public page exposes `<template data-shareable>` and renders a full-viewport, purple-branded social card at `#render-shareable`, using only the published name, portrait, cover, tagline and canonical URL. It is self-contained and does not load remote JavaScript. No account/draft/crew data or credentials are passed to the renderer.
- Speaker settings shows a **Social sharing image** section only while the press kit is published. It loads the current `sharing.image_url` automatically (an owner-initiated page visit, disclosing the public URL and owner IP to Shareable) and offers **Regenerate image**, which re-requests both the Open Graph and Twitter images with Shareable's `rebuild=true` to replace the cached render for the current publication version. Regeneration never republishes or sends draft data; newer saved information still requires **Update public profile**, which also rotates the version. Load failures show an actionable error and keep Regenerate available. The renderer must reach the public site and allow its host; localhost is not reachable from the hosted instance. The toolkit has no sharing-image section and never contacts Shareable. Unpublishing removes sharing URLs, the settings section and source metadata/template availability, but Shareable/social-platform caches and downloaded images cannot be revoked automatically.

## 3. Roles and ownership

| Capability | Member | Admin |
| --- | --- | --- |
| Browse active conferences, editions, and the member directory | Yes | Yes |
| Edit own profile | Yes | Yes |
| Manage own proposal library and submissions | Yes | Yes |
| Manage own manual attendance, reviews, and crew | Yes | Yes |
| Read accepted friends' reviews, plans, and submission participation | Yes | Yes, under the same friendship rules |
| Read another member's private proposal content or submission details | No | No |
| Create/edit/delete conferences and editions, import metadata/logos | No | Yes |
| View catalog trash and restore catalog entries | No | Yes |
| Promote/demote accounts, suspend/restore access | No | Yes |

- Admin is not a privacy bypass. This is an application/API access rule, not a claim that a hosting operator cannot access server storage.
- Production signup always creates a member; users cannot assign themselves roles through profile updates. Only in explicitly configured local development (`env=dev`), a newly created `admin@purpleroom.dev` account receives admin through verified signup or the CLI seed. All other new addresses are members, including the former local seed address. Existing account roles are unchanged; production has no email-based automatic admin grant. Historical migrations and explicit protected setup/admin-management workflows are not changed by this development default.
- An admin can manage another admin, but cannot demote or suspend the last active admin. The last active admin also cannot delete their account until another active admin has been appointed. The safeguard applies to self-management and concurrent requests under the same write lock.
- Suspension immediately denies subsequent authenticated requests and new sign-ins. Restoring access does not make old sessions valid again; the member must sign in afresh.
- Suspended accounts are hidden from normal directory, crew, review, attendance, and submitted-friend views. Their data and relationships remain stored for restoration. Account administration still lists them; an owner's blocked list can retain a suspended account.

## 4. Conferences and editions

### Conferences

- Admins maintain the shared catalog. Conference data includes name, optional website, optional logo, and any retained description.
- Conferences also have admin-managed topic tags, separate from the structured tags in speaker reviews. Tags are entered as comma-separated text in the form, normalised to trimmed/lowercase labels with collapsed whitespace, and deduplicated. Each conference supports up to 20 tags of 50 characters each. An empty list clears tags; omitting tags on an API update preserves them. Tags are visible to all signed-in members on conference cards/details.
- The directory is name-first: compact cards, four per row on wide desktop screens and fewer on smaller screens. It shows the next edition and viewer-scoped review count, without logos or placeholder descriptions.
- `/conferences` combines name/context/tag text search, selectable topic tags, and **Have editions with open CFPs**. Multiple selected tags match any selected tag; text/tag/CFP filters combine together. Filter state and sorting are kept in the URL, and Clear filters retains the chosen sort order. Empty results show guidance rather than suggesting the catalog is empty.
- The open-CFP filter matches a conference if **any** active edition is currently within its CFP window, not only the next edition. Zoned windows use server-derived UTC instants for opening/closing; unknown-timezone legacy edges retain their UTC calendar-date checks. Deleted editions, future opening windows, expired deadlines, and unknown closing dates do not qualify. An undated event can still have an open CFP.
- Directory sorting supports name A–Z/Z–A and next-edition date soonest/latest first. The default is name A–Z; date ties are broken by name. Conferences without a dated next edition stay last in **both** date directions. This sorts event dates, not personal submission dates or CFP deadlines.
- Cards show up to three topic tags with an overflow count and an Open CFP badge when applicable. Detail pages show all topic tags. Review summaries retain their independent friend-scoped visibility.
- Detail and edit views may show logos. An admin can prefill metadata from a website and import a logo by URL; importing never creates conference content without saving.
- Logo imports are validated and stored locally. Existing external logos are migrated on the next conference save, not during ordinary reads. A failed import leaves the conference unchanged.
- The current form omits conference descriptions. Saving unrelated changes must preserve existing descriptions.

### Editions

- Editions belong to a conference but have independent IDs, titles, dates, locations, links, notes, submissions, and attendance.
- Multiple editions may belong to the same conference in the same year.
- An edition title defaults to the conference name. Explicitly blank titles are rejected; custom titles are retained when changing the selected conference. Titles are displayed as entered, without appending a year—for example, **JSNation Berlin 26**.
- When moving an edition between conferences through the API, a title still equal to the previous conference name follows the new name unless a title is supplied explicitly.
- There is no separate Year input. First/last dates determine scheduling; dates may be unknown. An event's last calendar date cannot precede its first. Zoned CFP windows compare actual opening/closing instants; legacy or partially unspecified windows retain the calendar-date validation.
- Editions support city, two-letter country code, online flag, event website, CFP link, CFP opening/closing dates, and admin-maintained notes (“Worth knowing”). Every editable event/CFP date has its own IANA timezone selector, defaulting to the editor's browser timezone for new dates. Existing date-only values keep an unspecified timezone until the admin explicitly selects one or changes the date; saving unrelated fields must not invent a timezone or shift an existing date.
- First/last event dates remain calendar dates in their selected zones, not appointments with inferred start/end times. Event displays include the saved timezone only when it differs from the viewer's current browser timezone (see comparison rules below); date sorting and next-edition selection continue to use the stored calendar dates. System-created audit timestamps remain UTC instants, not user-editable date fields.
- Timezone selectors show a compact set of familiar regional names, such as **Central European Time**, rather than separate CET/CEST or fixed-offset choices. Shortcuts store location-based IANA zones; a saved/browser city covered by a shortcut keeps its exact identifier. **Choose a specific city** expands a searchable IANA city list for any other location. Searching alone never changes the selection, and unlisted saved zones remain selectable without being replaced. Daylight saving follows the selected date automatically; users never switch between winter and summer time themselves. Shortcuts are curated, not grouped by today's UTC offset (for example, Phoenix is not Denver).
- CFP opening is at 00:00 on its selected date/timezone. CFP closing includes a time, defaulting to **23:59**, and a timezone. The server validates IANA identifiers and HH:MM values, derives UTC instants using the offset on the selected date, and rejects nonexistent or ambiguous daylight-saving times rather than silently normalising them. When both edges are zoned, interval validation compares actual instants rather than local date strings. Omitted fields on updates retain stored values; changing a date/time/zone recalculates its instant.
- Closing deadlines are shown in the **selected CFP timezone**, not converted to the viewer's zone. Event dates and CFP labels omit the timezone name/offset when the saved zone matches the viewer's current browser zone, including canonical IANA aliases and cities in the same curated regional shortcut (such as Zurich and Amsterdam). Matching is not based on today's offset: distinct zones that temporarily share an offset still show labels. Closing times remain visible even when their timezone label is omitted. Selectors always show the saved selection.
- For different timezones, event/CFP labels use the same friendly regional names as the selector, falling back to the city identifier for zones without a shortcut. Deadline labels include the deadline-date UTC offset when supported by the browser (for example, **Central European Time, UTC+1** in winter and **Central European Time, UTC+2** in summer). Exact IANA identifiers remain stored internally and available in the city picker. A legacy closing date has no invented time/zone and is labelled **Timezone not set** regardless of the viewer's zone; its old UTC date-only behaviour remains until explicitly configured. New API callers that provide a closing timezone but omit the time get 23:59; older date-only API payloads remain compatible.
- Starting an edition from a conference can reuse the previous edition's location, links, and notes. It does not copy dates or advance a year automatically; the title starts from the conference name.
- Conference detail lists dated editions newest first, then undated editions. The next-edition summary selects the earliest edition starting today or later.
- The internal `year` column is compatibility metadata, not identity or display text. It is derived from the first day, or last day if no first day is known. Undated editions retain supplied/existing metadata or use the current UTC year.

## 5. Private proposal library and submissions

- Members create, edit, and permanently delete their own talks/proposals. Deleting a proposal also deletes its linked submissions and requires confirmation in the UI.
- A proposal can be linked to multiple editions. Multiple different proposals can be linked to one edition, but the same proposal/edition pair cannot be duplicated.
- “Add my talk” offers **From my library**, **New talk**, and **Topic to be agreed**. The third option records a submission without a linked proposal and creates no placeholder in the talk library. It has the same private status and submission-date controls as other submissions.
- Each member can have at most one unassigned opportunity per edition, alongside any submissions with specific talks. Different members can independently have unassigned opportunities for the same edition.
- Owners can later attach a library talk or create a new talk from the opportunity's **Attach a talk** action. This updates the same submission, retaining its ID, status, submission date, creation date, and other details. Attaching a proposal already submitted to that edition is rejected without merging or replacing either submission.
- Submissions track local plans and outcomes. Adding a talk in purpleroom **does not submit it to an external CFP service**.
- Proposal titles, content, private notes, submission IDs, individual submission totals, submission dates/timezones, and outcomes are owner-only—even from admins through the app. The submission-date editor has an IANA timezone selector; it defaults to the browser timezone for a new date, while existing unspecified dates are preserved until edited. Timezone metadata never appears in shared submission-participation payloads.
- Owners can change submission status/details or remove a submission without deleting the reusable proposal.
- Each submission has optional **private notes**, available in “Add my talk” for all three creation options and editable later in “The details of this submission”. Notes entered in the creation modal are retained when switching between options. These are specific to that edition/opportunity and separate from reusable talk notes. Only the owner can read/edit them, including when the submission has no attached talk; friends and admins have no access through the app. Empty notes clear the field, while status-only changes and attaching a talk preserve it.
- Creating a submission requires an active edition; a proposal, when supplied, must belong to the submission owner. Reassigning a proposal/edition validates the corresponding ownership/active-edition requirement. Owners retain access to existing submissions linked to deleted catalog items, including unassigned opportunities.
- Talks have shared details (title, duration in whole minutes 1–600 as one length or a range such as 20–45 (`duration_minutes` plus optional `duration_max_minutes`, which requires a start and must be above it; the form accepts `45` or `20-45` with a hyphen or dash, an equal range saves as one length, and partial API updates are validated against the stored other bound), audience level `beginner`/`intermediate`/`advanced`/`all`, free-text language, format `talk`/`lightning`/`workshop`/`keynote`/`panel`/`other`), up to 20 named **abstract variants** (label + text, e.g. short, detailed, translated), and private notes. Only the abstract varies; other details stay shared. Variants are edited in place, with no version history, submission snapshots or restore. The talk page (`/talks/{id}`) is itself the editor: the full talk form is shown inline with saved values, alongside its submissions and deletion, with no separate edit step or modal. Saving keeps the member on the page and confirms the save. **New talk** opens the same, empty form at `/talks/new`; creating it opens the new `/talks/{id}`. Title and variant fields show character/word counts; copy actions for a talk live in the Speaker toolkit's Papers section (§2). Editing or copying never changes a submission's status, date or notes and submits nothing externally. Migration 016 copied each non-blank legacy `abstract` once into an "Abstract" variant; the legacy `abstract` column and per-submission `abstract_override` remain stored, API-compatible data without UI, and unrelated edits must not clear them. All talk details and variants are owner-only, even from admins, and never appear in shared, participation, activity, toolkit (`GET /speaker`) or press-kit payloads.
- `/talks` presents the private library as cards: three per row on wide desktop screens, two at medium widths, and one on mobile. Each card shows the title, last-updated date, total linked submissions, and a stacked status bar. Each status label sits directly beside its count in a grouped badge so their connection is clear. Empty talks show zero submissions and a route to find a stage.
- Card statistics describe **current statuses**, not a history of transitions. Every linked submission counts once, including `interested` and archived-edition submissions; legacy `attended` is labelled explicitly. These private totals differ from friend-participation counts, which exclude `interested` and deduplicate people.
- Submission controls can be expanded on each card to inspect editions and edit statuses/details or remove submissions. Statistics update after changes; the title opens the full talk page. Charts have text counts and accessible summaries rather than relying on colour alone.
- Unassigned opportunities appear in a separate **Topics to be agreed** section on `/talks`, with edition links, private controls, and the attach action. The reusable cards sit under their own **Talk library** heading and description, separated from opportunities by spacing and a divider when both sections are present. Opportunities also appear under the edition's **My submissions** and in the owner's dashboard data. They do not inflate a talk's card statistics until attached to that talk. Deleting an unrelated library talk does not delete an unassigned opportunity.
- Talk titles are always private. The legacy `hide_title` field is retained but is not a privacy toggle in the current UI.

### Submission statuses

The selectable statuses are `interested`, `submitted`, `accepted`, `rejected`, `waitlisted`, `confirmed`, and `declined`. Historical `attended` values remain readable and are shown as a disabled legacy choice, not offered as a new choice. The API retains compatibility with that stored status.

Statuses are owner-managed, not a mandatory linear workflow. A newly linked proposal defaults to `interested`. Setting `submitted` fills an absent submission date with today's date in the submission's selected timezone (UTC for legacy/API rows with no timezone). New browser-created submissions send the browser timezone. Owners can edit dates/timezones separately; changing status or attaching a talk retains existing dates/timezones and notes.

### Friends who submitted

- An edition may reveal **which accepted friends have submitted** and their combined count.
- A member qualifies if they currently have at least one submission whose status is not `interested`. All other supported statuses qualify, including `declined` and legacy `attended`; no submitted date or history is required.
- Topic-to-be-agreed submissions qualify on the same basis, without revealing that their topic is unassigned. A member with an unassigned opportunity and several linked proposals still counts once.
- Each friend counts once, regardless of proposal count. The viewer never counts as their own friend.
- Status changes between qualifying statuses do not reveal a changed outcome. Moving the last qualifying submission to `interested`, or deleting it, removes that friend from the list/count.
- Non-friends, pending requests, blocked relationships, and suspended accounts do not qualify.
- Participation responses contain only member identity, never proposal titles, submission IDs, per-person totals, or statuses.
- A count of one may identify the participating friend. This is allowed because participation itself is intentionally shared with friends.

## 6. Manual attendance

- Members explicitly select **Going**, **Maybe**, or no marker (“Not going” in the control) on an edition page.
- A member can choose either attendance state without owning or submitting a talk, or after a rejected/declined submission.
- **Submission status has no influence on attendance.** No outcome, status change, proposal deletion, or submission deletion creates, modifies, or removes an attendance marker.
- The owner and accepted friends can see Going/Maybe markers. Non-friends cannot see a member's itinerary.
- Edition and dashboard participant lists include the viewer's own plans and eligible friends' plans. Member profiles show plans only to the owner and accepted friends.
- There is no submission-derived “speaking” group in shared views. No marker does not distinguish an explicit refusal from a member who has not made plans.

## 7. Crew and member discovery

The crew screen provides **My crew**, **All members**, **Requests**, and **Blocked**, with name search. The directory includes completed, active profiles and excludes members blocked in either direction. Directory membership alone grants no access to private plans or reviews.

### Requests and friendships

| Current relationship | Action | Result |
| --- | --- | --- |
| None | A requests B | One pending request, outgoing for A and incoming for B. |
| Pending A → B | A requests B again | Same pending request; no duplicate. |
| Pending A → B | B requests A or accepts | One mutual friendship; no second pending request. |
| Pending A → B | A cancels or B declines | No relationship. |
| Friends | Either participant unfriends | No relationship; friendship-based access ends in both directions. |
| Any | Either participant blocks | Pending request/friendship removed; blocking rules apply. |

- Self-requests and duplicate friendships are prohibited. Shared friends do not grant transitive access.
- Only the recipient accepts an incoming request. Either participant can remove their own pair relationship to cancel, decline, or unfriend as appropriate.
- Requests appear in-app, with an incoming count. There are no request, acceptance, or unfriend emails, and no separate notification inbox.
- Members may request again after cancel/decline/unfriend, subject to request rate limits. There is no additional per-pair cooldown.
- Friendship grants access to existing as well as future reviews, participation, and plans. Unfriending revokes it on subsequent reads; previously seen information cannot be recalled.

### Blocking

- Blocking removes pending requests and friendships, prevents requests in both directions, and removes friendship-based visibility.
- The pair cannot browse each other through the ordinary member directory/profile views. Blocking does not remove shared catalog entries.
- Owners can view their own blocked list and unblock members. Blocking sends no notification.
- Unblocking removes only that member's block, not a reverse block. It never restores a friendship or pending request automatically.

## 8. Speaker reviews

- Each member can maintain one review per conference, shared across all its editions.
- A review contains recognised structured tags, optional free text, and an optional yes/no “would submit again” recommendation. Repeated tags are deduplicated.
- Authors can create, edit, and delete their own reviews. Admin status does not grant editing or private viewing of others' reviews.
- Reviews are visible only to their author and accepted friends. This applies to historical reviews too.
- Counts, tag totals, return recommendations, card summaries, edition-side speaker intel, and review activity use the same viewer-specific scope. Non-friends' review aggregates must not leak through summaries.
- Review tags cover speaker support, audience, CFP process, personal experience, and organisational concerns; available keys are defined in the frontend/backend constants.

- The brand tagline is **{ where speakers swap notes }**, including braces, used in the sign-in screen, desktop app header, and page metadata. Transactional sign-in emails omit it.
- The login/verification screen displays a **v0 / early beta** notice warning about bugs and rough edges and welcoming feedback; it remains visible during code entry. The README carries the same warning.
- App branding uses the supplied SVG assets in `visuals/logo/`: full light/dark logos for navigation and sign-in/setup/onboarding, the small mark for the mobile header and dashboard callout, and the simplified favicon for browser tabs. Logo variants follow the app's selected appearance, not just the OS setting. Email branding remains text-based without remote images.
- The footer shows the app version on signed-in and login/verification pages. Development and local builds without version metadata display `version: dev-local`; GitHub Actions builds display `version: dev-HASH`, where HASH is the short commit hash being deployed.
- The Vite development server uses the browser page title **DEV Purple Room - { where speakers swap notes }**. Built/production pages retain **Purple Room - { where speakers swap notes }** without a DEV prefix.

Unknown deadlines are not included. Day-count badges use the CFP timezone's calendar date when known; an elapsed timed deadline is closed even earlier on the same date.

These text/background pairs meet WCAG AA normal-text contrast (at least 4.5:1), including primary-control hover states.

## 10. Deletion, restoration, and retained data

- Account deletion permanently removes the account/profile, username claim, private speaker toolkit and published press kit, owned talks and linked/unassigned submissions (including private notes and abstracts), reviews, attendance, crew requests/friendships/blocks, retired comments, and related historical invitation records. All outstanding code/legacy login requests for that email and user-bound login tokens are removed. Other members' data is preserved.
- Shared conferences and editions—including their notes, logos, and trash status—remain with their existing IDs and content. Their creator attribution becomes `null`; deleted authors no longer appear in activity. This exception is stated in the confirmation dialog rather than promising to erase shared catalog contributions.
- Current and other-device sessions stop authenticating after deletion. User IDs are never reused, preventing old sessions from matching a new account. Signing up again creates a new empty member account; it does not restore deleted content or relationships.
- Profile images (including retained replacements) and related encrypted invitation payloads are queued for physical removal in the deletion transaction and normally removed immediately after commit. They are inaccessible once the account/token is removed; filesystem failures remain in a durable, bounded cleanup queue retried on subsequent normal API requests. Unrelated images, conference logos, invitation payloads, and the shared invitation key are preserved. Existing server backups follow the operator's retention policy; deletion is not a promise to erase every backup immediately.
- Conferences and editions are soft-deleted, not permanently erased through the app. Only admins can delete or restore them.
- A deleted conference makes all its editions unavailable in the ordinary catalog without rewriting their individual deletion markers.
- Restoring a conference reveals its editions except those independently deleted. Restore a parent conference before restoring an edition under it.
- Trash lists entries deleted in the last 90 days. That window is a listing filter, not a scheduled permanent-deletion policy.
- Personal proposals/submissions, reviews, attendance, stored logos, and relationships retain their IDs and links across catalog soft deletion/restoration.
- Existing users receive no automatic friendships during upgrades. Explicit attendance is preserved; submission-derived attendance is not materialised.
- Calendar subscriptions, signup invitations, and conference/edition comments (“Notes from the crew”) are not active features. Their former routes/controls are absent, including old secret calendar feeds and invite acceptance.
- Historical comments, invitation rows/encrypted storage, calendar tokens, abstracts, and compatibility fields remain stored except for data explicitly removed by owner-controlled account/content deletion. Removing a UI feature is not permission to erase its underlying data.
- Private proposal notes and admin edition notes remain active; they are not the removed crew-comments feature.

## 11. Essential invariants for future changes

1. Anonymous visitors cannot retrieve private member or catalog content; exceptions are explicitly published speaker-profile snapshots and stable public speaker-image capability URLs.
2. Profile completion precedes member discovery and normal app access.
3. Catalog/account administration is authorised server-side; UI guards alone are insufficient.
4. Admins do not bypass ownership or friendship privacy.
5. Pending, blocked, or suspended relationships grant no friendship-based access.
6. Submission participation counts distinct friends with any non-`interested` submission, never proposals.
7. Attendance remains entirely independent of CFP outcomes.
8. Review aggregates and activity follow the same privacy rules as their source data.
9. Unfriend/block/suspension revoke applicable access, including nested API responses and summaries.
10. The last active admin remains protected from demotion, suspension, and deletion; restored accounts cannot reuse sessions invalidated by suspension, and deleted identities cannot be reused by later accounts.
11. Upgrades and feature removals preserve unrelated stored data and identifiers.

Keep these covered by regression tests when changing affected features. They are behavioural contracts, not permission to broaden scope or change policy silently.

## 12. Not currently provided

Calendar subscriptions, signup invitations, crew comments, anonymous catalog/member browsing (apart from opted-in press kits), named groups, generic social posts, likes, direct messages, public friend lists, mutual-friend counts, an independent notifications system, self-service email changes/data export, and abuse-reporting workflows are outside the current product. Adding any requires an explicit product decision and an update here; residual schema/helpers do not imply an active feature.
